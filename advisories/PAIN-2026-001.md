## 02. Root-Cause Forensic Analysis (Runtime & Protocol Level)

Observed: The advisory metadata names zend_handle_delayed_oom() and commit 3584a98bda. Inference (from naming only): the zend_ prefix places the code in the Zend Engine core, and 'delayed OOM' points at memory-exhaustion handling. If that reading holds, the flaw is a memory-safety class defect in the engine. It is reachable regardless of framework (Laravel, Symfony, WordPress, WooCommerce) and invisible to any tool that inspects PHP code or Composer packages. Treat this as a hypothesis until you have read the commit diff.

Do not take fixed version numbers from a blog post, including this one. Resolve them mechanically: the commit hash maps to the release tags that contain it. The script below does that, then checks what is actually executing.

Inference (operational): php-fpm workers are long-lived processes forked from a master. Upgrading the package on disk does not change the binary mapped by an already-running master. After an upgrade, /proc/<pid>/exe resolving to a path marked '(deleted)' means the old binary is still serving requests. Restart the service, not just the file.

```bash
// Verify the running binary, then derive fixed releases from commit 3584a98bda
#!/usr/bin/env bash
set -euo pipefail
# 1. What is actually serving traffic (run inside the container / instance)
php -r 'echo PHP_VERSION, PHP_EOL;'
php-fpm -v | head -n1
readlink /proc/$(pgrep -o -f 'php-fpm: master')/exe   # '(deleted)' suffix = package upgraded, master never restarted
# 2. Which release tags contain the fix commit (authoritative; no guessing)
git clone --filter=blob:none --no-checkout https://github.com/php/php-src.git /tmp/php-src
git -C /tmp/php-src tag --contains 3584a98bda | grep -E '^php-8[.][34][.]' | sort -V | head -n 6
# 3. Read the change itself before trusting any summary
git -C /tmp/php-src show 3584a98bda --stat
```


## 03. Immediate Zero-Downtime Triage (Non-Breaking Mitigation)

Inference: The controls below reduce attack surface while you schedule the runtime upgrade. They come from HadayaLab's triage profile for this advisory pair. Confirm applicability against the advisory text. They do not replace the patch.

Step 1, PHP-FPM: disable the session upload-progress path. Most applications never use it. A progress bar that polls $_SESSION for upload state is the only common casualty. Validate the config, then reload. A reload re-reads pool configuration without dropping in-flight requests, but it is not proof that the binary was swapped.

Step 2, Nginx: execute PHP only through the front controller, and never from writable paths. This limits what a post-exploitation write can run.

Step 3, Google App Engine: force fresh instances onto the current runtime by redeploying a new version and stopping the old one. Do not assume the console's runtime label applies to already-running instances.

```ini
// PHP-FPM pool (e.g. /etc/php/8.3/fpm/pool.d/www.conf)
php_admin_flag[session.upload_progress.enabled] = off
php_admin_flag[expose_php] = off

; validate, then apply without dropping in-flight requests:
;   php-fpm8.3 -tt && systemctl reload php8.3-fpm
```

```nginx
// Nginx: restrict PHP execution
# Laravel / Symfony: only the front controller may execute PHP
location = /index.php {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
    fastcgi_param PHP_ADMIN_VALUE 'session.upload_progress.enabled=0';
    fastcgi_pass unix:/run/php/php8.3-fpm.sock;
}
location ~ \.php$ { return 404; }

# WordPress: do NOT use the catch-all above (it breaks wp-login.php). Use this instead:
# location ~* ^/wp-content/uploads/.*\.php$ { deny all; }
```

```bash
// Google App Engine: replace stale instances
gcloud app versions list --service=default
gcloud app instances list --service=default
# redeploy forces fresh instances on the current runtime image
gcloud app deploy app.yaml --version=v20261024 --promote --stop-previous-version
# for any instance you cannot drain via redeploy:
gcloud app instances delete INSTANCE_ID --service=default --version=OLD_VERSION
```

## Frequently Asked Questions

### Does composer audit detect CVE-2026-109618 or CVE-2026-109619?
No. composer audit checks the packages in composer.lock against an advisory database. These CVEs are filed against the PHP engine. Verify the interpreter by running php -v inside the live container or instance and comparing it with the fixed tags you resolve from commit 3584a98bda.

### How do I find which PHP 8.3 / 8.4 release fixes PHP2Shell without trusting a third-party summary?
Clone php-src and run git tag --contains 3584a98bda. Every tag in the output contains the fix. Cross-check it against https://www.php.net/ChangeLog-8.php and the two GitHub advisories (GHSA-w8hw-w9fx-j79w, GHSA-6wmf-4rv5-p3rp).

### My Laravel app passed its last security audit. Why would I still be exposed?
An application-level audit tests your code and dependencies. An engine-level defect lives below both. Passing that audit says nothing about the PHP binary your workers run, or about whether those workers were restarted after the runtime was updated.

### Will disabling session.upload_progress break my WordPress or WooCommerce site?
In most deployments, no. The setting only affects code that reads upload progress from the session, such as custom progress bars. Test it on a canary pool first. It is a compensating control, not a patch, so schedule the runtime upgrade regardless.
